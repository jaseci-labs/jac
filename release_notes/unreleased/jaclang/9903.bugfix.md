- **Fix: a websocket walker or function runs in a request context of its own** (#9863): the HTTP path gets a fresh execution context and database session per request from the request-context middleware, but a websocket message never passes through that middleware, so the executor took the process-global context as the call's parent and ran every websocket walker and function on the process-global session. Any non-request code that had read the graph through that session (a background thread polling `[root -->]` is enough) left its transaction open, and websocket calls then read through that old snapshot: a user registered afterwards got `Root anchor <id> for user '<id>' does not exist in the anchor store` on every websocket call while their HTTP calls worked. Concurrent websocket calls also shared one identity map and one transaction, a write made while a websocket result was streaming stayed uncommitted, and a standalone file served in-process could resolve a different database over websocket than over HTTP. A request context is now opened in one place, `RequestScope` (`jaclang.server.request_scope`), reached through `JacAPIServer.request_scope()`: the HTTP middleware enters it per request, the websocket loop per message (through the end of a streamed result; a stream whose delivery is cut off, for example by the client disconnecting, is closed first, so its unfinished work is aborted rather than committed when the scope ends), and both schedulers per run. The executor no longer falls back to the process-global context: `ExecutionManager.spawn_walker` and `execute_function` called outside a request scope raise instead of sharing that session, so code that drives the execution manager directly wraps the call in `with server.request_scope() { ... }`.
