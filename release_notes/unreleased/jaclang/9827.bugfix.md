- **Fix: a scale deploy of a known jac version no longer spends the GitHub API quota**: the preflight, each pod and sealing binary download and the admin console lookup asked the anonymous Releases API (60 requests per hour per IP) for assets whose URLs the version already determines, so a shared CI runner whose quota was used up failed the deploy with `HTTP Error 403: rate limit exceeded` before it reached the cluster, whatever `GH_TOKEN` held. An exact `[project] jac-version` pin, or a range once it has resolved, now downloads from `releases/download/v<version>/` directly and probes the pod and sealing assets with `HEAD` in the preflight, so a missing release, arch or checksum still stops the deploy early with a message naming it, and a transient failure names the URL and says to retry. Checksum verification and the admin console's refusal to stage an unverified asset are unchanged. `latest` still resolves through the API, and those requests now send `GH_TOKEN` (or `GITHUB_TOKEN`) as a bearer token, only to `api.github.com` and never across a redirect. An exhausted quota is reported as such, naming `GH_TOKEN` and the `jac-version` pin as the two ways out. A range pin whose release listing fails now reports that failure (the quota, or a retryable network error) instead of claiming the pin matches no release, and a token GitHub rejects with a 401 is retried once without it, with a warning naming `GH_TOKEN`/`GITHUB_TOKEN`, so a stale token does not break a deploy that worked anonymously.
