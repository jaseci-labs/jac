- **Scale: revision based rollback and a bundle retention contract**: a deploy already leaves a complete rollback target in the cluster, since the pod image is constant across versions and deploy patches rather than recreates, but nothing exposed or protected it. `revision_history_limit` is now a declared `KubernetesConfig` field that lands on every Deployment, defaulting to the 10 the API already applied, so rollback depth is something a consumer can read back instead of inferring. `list_revisions` reports an app's releases, identified by the bundle digest, and `rollback_to` reverts every service of a release to whichever revision carried it, services first and the gateway last, resolving that fleet from the cluster with the same label selector `destroy` uses rather than from a route table the SDK never fills, waiting for the reverted fleet to come back before reporting success. It refuses when any service no longer has a retained revision, rather than half reverting an app onto two versions at once. The fleet waiter now holds until the Deployment controller has observed the patch and every replica runs the new template, instead of accepting any single ready replica, which a just patched Deployment still has from the outgoing one. Rollback restores code, not configuration, and the boundary is worth stating plainly: a release is its bundle digest, a reverted pod template reads whatever the `[scale.secrets]` Secret currently holds, and the restored template does not carry the config marker of the release it came from. Since a config-only redeploy keeps the same bundle, it is grouped with the release it shares that bundle with rather than listed separately, so it is not selectable in `list_revisions` and rolling back to that release restores the newest revision carrying the digest. Configuration is therefore deliberately out of scope here rather than partly supported. `revision_history_limit` is declared in the `[scale.kubernetes]` schema, and `0` keeps no history at all, which makes a rollback impossible. `bundle_keys_from_pod_spec` and `referenced_bundle_keys` give consumers the retention contract that a bundle referenced by a retained revision is never deleted, reading the keys back out of the init container the injector itself builds so the writer and the reader cannot drift, and `ScaleClient.bundle_keys` exposes it beside `revisions` and `rollback` so a consumer reaches all three without constructing a target itself.
