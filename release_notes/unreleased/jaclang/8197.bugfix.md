- **Fix: a JIR cache newer than its source is no longer valid by that fact alone**: `is_module_cache_valid` accepted a cached module JIR on an mtime comparison, and consulted the module key -- the only thing that compares the node schema digest, the codegen fingerprint, the placement pins, the config kind space, the service cut, the client kind, the codespace mode and the JIR format version -- only on the branch the mtime check had already rejected. Since the cache filename is derived from the source path and Python version alone, a schema change with unchanged sources served every warm cache straight into a decoder that no longer agreed with it: #8181 shortened `Test`'s node spec by one field, so a pre-#8181 cache decoded positionally against the new spec consumed the old `TEST_COUNT` value as the next field's data, failing to decode or silently yielding a corrupt scope and symbol tree. The module key's inputs now split into an environment fingerprint (toolchain facts plus the cheap per-source config facts) and the expensive source and annex content hashes, with `compute_module_key` composed from that split so the inputs keep one definition. Every module JIR carries the environment fingerprint in a new `SEC_ENVKEY` section, and `is_module_cache_valid` compares it before it looks at any mtime, failing closed when it is absent. The mtime fast path still skips the content hashing it exists to skip.
- **JIR format version 19 -> 20**: module caches are now required to carry the environment-fingerprint section, and the bump flushes the caches #8181 poisoned on every machine that pulled it, including the precompile seeds and sealed manifests that never consult the new section.
