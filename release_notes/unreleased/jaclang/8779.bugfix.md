- **Fix: jac-scale routes HTTP-activated microservices through the KEDA interceptor automatically (#8779)**: `http_activation.enabled = true` on a service correctly created its `InterceptorRoute` and `ScaledObject` (#7709), but nothing in the runtime actually sent traffic through the interceptor: the gateway's forward path and sv-to-sv RPC calls both resolved a scaled-to-zero service's own ClusterIP Service directly, so a request that arrived after the pod scaled to zero was refused instead of waking it (#7959). Both paths now resolve the interceptor's address and set a `Host` header equal to the service's own real Service DNS name, matching the KEDA HTTP Add-on's documented routing pattern, so an operator no longer has to wire the gateway or Ingress to the interceptor by hand. The interceptor routing rule for cluster-internal traffic is derived automatically from the same source used to resolve peer URLs, so the two can no longer drift apart. `walker_call` also now consults the live Kubernetes service registry the same way `service_call` already did, instead of always falling back to a stale, deploy-time-baked URL. The deploy also stopped injecting a leftover `JAC_APP_<PEER>_URL` env var for every peer regardless of activation status; since the runtime checked that env var before ever considering the interceptor route, it silently defeated this entire fix, so it is no longer injected for HTTP-activation peers. Route learning and OpenAPI aggregation fetch each service's `/openapi.json` over the same resolved route, so those fetches now carry the same `Host` header; without it an activated service's spec fetch missed every interceptor rule and its routes were never learned, leaving only its prefix-routed paths reachable. `[scale.kubernetes.http_activation] interceptor_service_address` is now part of the config schema, so pointing at an HTTP Add-on installed outside the default `keda` namespace no longer draws an "unknown key, defaults apply instead" advisory for a value that was in fact applied.
