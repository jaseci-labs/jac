- **Replicas booting together against a fresh database no longer race each other to death** (#8166): `ensure_schema` decided whether to run schema DDL from a stamp row that is null on every replica of a new database, so every replica ran the DDL. The gate added in #8132 is a `threading.Lock` plus a `set`, which excludes this process's threads and nothing else, and replicas are separate processes. `CREATE ... IF NOT EXISTS` is not concurrency-atomic: two sessions both pass the existence probe and then race the catalog's unique indexes, so the losers died with SQLSTATE `23505` on `pg_type_typname_nsp_index` or `pg_class_relname_nsp_index` and crash-looped until a restart happened to find the schema present. One creator per database is now elected through Postgres itself, with a session-level advisory lock on a key derived from a fixed constant (deliberately not from the connection, since two replicas that spell the same database differently would otherwise get two different keys and no election at all). The lock is taken before the stamp is trusted, the stamp is re-read under it so losers see the winner's work and no-op, and it is released in a `finally`; a crashed holder releases it by disconnecting. The wait is bounded and polls rather than blocking, re-reading the stamp between attempts, so a loser wakes as soon as the winner stamps instead of at the timeout, and a database where the election is unavailable at all still boots. Because the election only binds jac processes, `23505` / `42P07` / `42710` are additionally treated as "a concurrent creator won": the stamp is re-checked and the DDL replayed once, since every statement is `IF NOT EXISTS` and the winner's objects are simply skipped. The existing `55P03` reap-and-retry path is unchanged and composes with it, and an unrelated SQLSTATE still raises rather than being mistaken for a peer. The failure was also reported as the wrong thing entirely: `shared_store()` collapsed every cause to `None`, cached that `None` under the current key, and the identity manager rendered a hardcoded "no `[scale.database]` url / `JAC_DB_URL` resolved and the embedded server could not be provisioned" even when a url had resolved and the real error was a lost catalog race. `shared_store()` now records why it failed and exposes it as `shared_store_failure()`, separating nothing-resolved from a provisioning failure, a connect failure (naming the host, port and database it could not reach, and which knob resolved them) and a schema failure; the identity manager and the `jac_admin` Postgres health probe render that reason verbatim, so the missing-url claim appears only when nothing was in fact resolved. A failed attempt no longer commits the holder key either, so one bad moment at boot is retried rather than pinned for the life of the process, which had also frozen the health probe on a stale verdict. Finally `scale_db_url()` imported `get_scale_config` from `jaclang.scale.config.plugin_config`, which does not define it, and swallowed the resulting `ImportError` with a bare `except`, so the `[scale.database] url` that these messages name as the fix could never resolve and only `JAC_DB_URL` ever worked; it now reads the config loader that owns that function.
