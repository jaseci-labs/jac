- **Scale: a dry run shows the rate limit the project configured**: `_render_cluster_wide` read `requests_per_minute` from the normalized microservices config, but `normalize_microservices_config` builds the `rate_limit` dict from a fixed key set (`enabled`, `per_ip_rpm`, `per_user_rpm`, `burst_multiplier`, `exempt_paths`) and never emits that key, so the read was unreachable rather than misnamed: no `jac.toml` could produce the rate-limit line, and adding `requests_per_minute` to the table did not help because an unrecognised key does not survive normalization either. The limit was still enforced, since the middleware reads the real keys, so what was broken is that `--dry-run` could not confirm a rate limit before the deploy that applies it. The plan now renders the loader's contract: both the per-IP and per-user tiers, which were equally invisible before, plus the burst multiplier that sets the effective ceiling, and it says so explicitly when a limit is enabled with both tiers at zero and therefore builds no limiter at all. The renderer restates no defaults, so the plan shows what the loader produced. The test that appeared to cover this line went, too: it called the renderer directly with a hand-built `requests_per_minute` dict, under a comment noting that a loader-sourced `rate_limit` never reaches that branch, and is replaced by plan tests that run through the real config loader plus a `jac start --scale --dry-run` subprocess e2e.
