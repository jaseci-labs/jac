- **Fix: augmented assignment on a module-level variable and `bool(...)` give Python's answers natively**: on the native backend, `g /= 2` on a float assigned in a `with entry` block stored the right-hand side (`2.0` instead of `5.0`), and `%=` on such a float did the same; the module-global store now computes every scalar augmented operator the way a local does. Module-level variables and locals now share one lowering, so `d |= {...}` on a module-level dict merges instead of keeping only the right-hand side, complex, set and bytearray augmented operators work at module level, `list *= n` and `list += other` update the list in place (aliases see the change), `str *= n` repeats, and an augmented operator with no native lowering is a compile error (E5092) instead of a silent store of the right-hand side. `bool(...)` returned a 0/1 integer instead of a bool, so `print(bool(0))`, `str(bool(0))` and `f"{bool(3)}"` showed `0` and `1`; it now returns a bool, and `bool(nan)` is `True` as in Python. A bool used as a count or an integer argument (`"x" * True`, `[1] * bool(1)`, `divmod(True, 1)`, `round(True)`, a set of bools in a function) now behaves as `1` or `0` instead of crashing the compiler or printing `True`.
