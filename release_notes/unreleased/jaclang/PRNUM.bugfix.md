- **Fix: `run_request` re-runs a write outside a request the way a request is re-run**: since 0.40.2 a write conflict outside a request rolls the transaction back and raises `TransactionLost`, so code that writes from a worker thread or background loop has to run its writes through `Jac.get_context().mem.run_request(unit)`. `run_request` re-ran the unit with a loop of its own: five immediate attempts, no waiting for the node the unit lost, and no `[serve]` settings, so on a busy node it failed where the same write in a request queued and succeeded. It now follows the request policy: `on_conflict`, `conflict_max_attempts` and `conflict_backoff_ms` apply (so the default is 5 attempts, not 6), the next attempt waits its turn on the node it lost (on a thread that runs an event loop it still re-runs at once, so the loop is never blocked), and a unit that gives up releases that turn. `on_commit` callbacks registered by an attempt that lost its conflict, or by a unit that gave up, are dropped instead of running when the context closes. Called inside a walker or function, `run_request` now runs the unit once and leaves the commit and any re-run to the request, instead of rolling back the request's own writes on a conflict. The contract (the unit is re-run from the top, so model calls, mail and other external calls go before it) is documented under [Persistence -> Concurrent writes](../../reference/persistence.md#concurrent-writes-check-then-create-and-convergence).
