- **Archetype registration no longer depends on module import order**: node and edge classes register with the serializer through `Archetype._subclass_hooks`, which `__init_subclass__` runs for each *new* subclass, and nothing back-filled the classes that already existed when a hook was installed. So an application whose archetype modules loaded before `jaclang.runtimelib.serializer` never registered them, and every later read of their anchors was refused (`Refused to deserialize unregistered class: ...`) and the anchor dropped, handing the caller an empty result indistinguishable from the record not existing while the rows sat intact in the database. Any unrelated change that perturbed import order flipped a suite between passing and failing. Hook installation now goes through `Archetype.install_subclass_hook`, which walks the existing subclass tree transitively and applies the new hook to classes that already exist (skipping `__jac_base__` bases, idempotent per hook, and isolating a raising hook so one class cannot abort the rest). As a backstop, `Serializer._get_class` now resolves an unregistered archetype from its own module and registers it for subsequent reads, so resolution no longer depends on registration timing at all. The deserialization allowlist keeps its teeth: resolution prefers modules already loaded, refuses to import a module whose top-level package this process never loaded, and only accepts a `type` that is an `Archetype` subclass whose own `__module__` and `__name__` match the name being resolved. Manually calling `Serializer.register(MyNode)` at module scope is no longer needed as a workaround.
