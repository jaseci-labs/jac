- **An unlowerable construct in a client-pulled module now fails the build with its own diagnostic** (#8375): a markerless module reaches the browser only by being *pulled*, meaning a client module imports it and the placement solver stamps those elements client. If ES lowering of that module then failed, the bundler demoted every pulled element in the file back to the server and deleted the diagnostics that explained why. `jac check` stayed green, the demoted module emitted no `export` at all, and importers that had already been lowered kept importing names it no longer provided, so the build died inside Rollup on `"stepXY" is not exported by "compiled/geometry.js"`, naming a helper that was never the problem. The real cause, an `E5018` pointing at the exact unsupported pattern, survived only as a dim `note:` on stderr. An ES lowering failure in a client-used module is now a `ClientBundleError` carrying the full diagnostic, source excerpt and help text; it is raised where the failure happens instead of being swallowed and re-surfaced as an unrelated bundler crash. `E5018` also names the rewrite per construct rather than saying only that the pattern is unsupported: `match` itself lowers to the client, so a binding inside an or-pattern now advises splitting the `|` alternatives into one `case` each, and the stale advice to move the match to a server or native codespace, which is what stranded the importer in the first place, is gone. Narrowing the demotion to just the failing element, and reconciling importers against a changed placement, are tracked separately.
