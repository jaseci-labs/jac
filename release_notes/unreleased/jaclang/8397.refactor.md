- **One class layout model per program, built from the type system's linearization**: archetype layouts were held per-module on `module.gen.layout_registry`, keyed by bare name, and the native codegen merged other modules' registries into the consuming module's by aliasing the layout objects themselves, then repaired the result with `adopt_imported_bases`. A bare-name collision resolved first-writer-wins in import-walk order, a merged layout could be mutated by whichever module compiled next, and layouts were assigned before their imported ancestors were known. There is now a single `JacProgram`-scoped model keyed by `<declaring module>::<name>`, covering the import closure. Linearization is read from `compute_mro_linearization` rather than recomputed, so the layout model and the type checker agree by construction, and laying a class out recurses through its ancestors first, which removes the repair pass entirely along with `extended_mro`, `adopt_ancestor_slots`, `relax_vtable_header`, `LayoutPass._compute_c3_mro` and `LayoutPass._topo_sort`.
