- **Feature: byLLM generates images from an `Image` return type**: `def draw_poster(subject: str) -> Image by painter();` now dispatches to the provider's image-generation endpoint instead of a chat completion, and `list[Image]` keeps every image the provider sent. Until now byLLM had exactly two provider entry points, both chat completions, and the declared return type selected the output schema but not the modality, so an `Image` return reached the output-schema builder and failed with `Unsupported type for schema generation: <class 'bytes'>` - a message about the union inside `Image.url`, not about the unsupported operation. `BaseLLM.invoke`/`ainvoke` now branch on the return type before the streaming and tool checks, into a `model_call_image` seam that `Model` serves with `litellm.image_generation` and `MockLLM` serves from its scripted queue, so an image call can be tested at the network boundary like any other. `n`, `size`, `quality`, `style`, `response_format`, `user` and `timeout` are forwarded from the `by` call when set; `response_format` defaults to `b64_json`, so the returned `Image` carries the bytes as a data URL rather than a provider URL that expires. The result is an ordinary `Image`, so it feeds straight back into a vision call. A configured `base_url` is honoured on a generation call the way it is on a completion, and a `system_prompt` is prepended to the prompt while byLLM's built-in chat persona is dropped, so it cannot steer the image model. Combinations that cannot work are refused with a `ConfigurationError` rather than silently mishandled: `tools=` and `stream=` (generation is one call), an `Image` or `Video` argument alongside an `Image` return (the generation endpoint takes text only, so there is no image editing yet), and the `proxy` and `http_client` transports, which do not carry a generation call.
