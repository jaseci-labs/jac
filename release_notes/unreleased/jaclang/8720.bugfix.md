- **Loop `else` clauses finally run** (#8629): `for i in xs { ... } else { ... }` and the same form on `while` loops parsed cleanly but the else body never executed when the loop exhausted normally on the native and JavaScript backends. The native backend now routes each loop's exhaustion edge into a dedicated else block across all loop forms: `while`, C-style iter-for, indexed range/list/dict/set/str loops, iterator-protocol loops, and chunked loops. Else-bearing `flow for` loops take the sequential lowering instead of the parallel worker/join outline, which has no else machinery. The JavaScript backend recovers the same semantics with a labeled block: exhaustion falls through into the else statements while breaks inside the loop are rewritten to labeled breaks. Labels appear only when a break could actually bypass an else.
- **Control flow inside a loop's `else` block is now well-defined** (#8629): `break` inside an else block exits only the loop that owns the else -- the rest of that else suite is skipped while an enclosing loop keeps iterating. `continue` inside a loop's else block is rejected with a new diagnostic (E0059): the else suite runs after the loop has already exhausted, so there is no next iteration for it to skip to.
