- **PgStore LISTEN and NOTIFY now agree on what a channel is**: `listen()` ran `LISTEN` on a sanitized identifier (name lowercased, every non-identifier byte folded to `_`) while `notify()` published the raw name through `pg_notify`, which accepts any string, so two silent failures rode together for any channel carrying a `:` namespace separator: `notify("cache:invalidate", ...)` published to a name nobody was listening on and lost every message, and a subscriber of `cache:invalidate` was instead woken by traffic published to the logically distinct `cache_invalidate`, because the listen loop matched subscribers by sanitized name too. Neither side raised or logged anything. Both sides now derive the Postgres channel through one canonical mapping, and delivery matches subscribers on the exact channel name they asked for. A name inside the 63-byte budget Postgres allows for a channel travels verbatim, quoted as a delimited identifier on `LISTEN`, so separators and mixed case survive intact and an external publisher can reach a jac subscriber with a plain `pg_notify` on the same name. A name past that budget, which Postgres cannot represent at all, maps to a stable hash-disambiguated identifier and carries its raw name in a small JSON envelope, so it is neither silently truncated on the listen side nor rejected on the notify side and still cannot cross-deliver. The WebSocket `PgBackplane` drops its own copy of the sanitizer and only namespaces channels as `jac_ws_<channel>`, so `room-1` and `room_1` are distinct broadcast channels.
- **A store's LISTEN thread now stops when the store is done with it**: `listen()` had no counterpart, and the background thread that carries notifications reopened the side connection on its own, so it could raise a fresh connection at the very moment its store was closed, then keep polling a database nobody was using. `PgStore.unlisten(channel)` drops a subscription, issues `UNLISTEN` when no other subscriber shares that channel, and parks the thread once the last subscriber leaves; `close()` does the same and joins the thread instead of leaving it to notice a flag on its own schedule. The thread now uses only the connection it was given and exits when that connection goes away, so it never resurrects one behind the caller's back.
