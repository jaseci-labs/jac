- **Follow-ups from the 0.36 Postgres fix batch**: four leftovers from reviewing #8097 / #8098 / #8099 / #8100 / #8101 / #8102 / #8103, all in the same family of "the runtime quietly stops seeing something and only a restart or a human fixes it". (1) The serializer's failed-import cache was a set written on the first failure and never cleared, so one import error made a module dead for the life of the process: every later read of an anchor whose class lives there resolved to `None`, was dropped and quarantined, and the caller got an empty result indistinguishable from the record not existing. The failure that matters is not the deterministic kind, it is a circular import resolved under concurrency, where the thread that sees the half-initialised module raises and the module is fine a moment later. The cache is now a bounded per-module backoff (attempts plus the time of the last failure) that still allows at most one import attempt per window, doubling per consecutive failure up to a ceiling, and drops the record as soon as the module is resolvable again, including when it turns up in `sys.modules` because another thread finished the import. (2) `PgStore` guards first-use schema DDL behind `_schema_gate` plus `_schema_ready`, and the scale shared store ran `ensure_schema` past both, so a shared store and a request-scoped store could run schema DDL against the same database at once and whichever lost the DDL lock surfaced `SessionConflictError` on an ordinary first request against a fresh database, which is exactly what a cold multi-replica fleet looks like. The gate is now the entry point (`PgStore.ensure_schema_once`), every production caller goes through it, and the scale store passes the project's real `[database] indexes` promotions instead of `{}` so the memo the gate keeps is honest. (3) `Archetype._subclass_hooks` was still a plain mutable list, so the next caller to reach for `.append` would silently reintroduce #8049 with a hook that never sees the classes that already exist; it is a tuple now, so a raw append raises instead, and `install_subclass_hook` / the new `uninstall_subclass_hook` are the only ways in. (4) A scratch database left by a pod that died without running its exit handler was never reaped, because the recorded pid cannot be checked from another host and every pod gets a fresh hostname. Scratch registry records now carry a heartbeat, refreshed once a minute while the database is open, and a record is reclaimed only when its pid is checkable from that host and gone, or when nothing is connected to the database, its heartbeat has been silent for 30 minutes (24 hours when the pid answers and may be a recycled one), and an earlier pass at least an hour before already found it that way. Two separated observations are required because those signals are not independent: one partition or one saturated connection pool stops the heartbeat and drops the store's connection at the same instant and for the same reason, so a single silent window would let a transient outage condemn a live run. Any heartbeat clears the mark, a heartbeat-grounded drop is never forced (so an owner that has reconnected vetoes it at the server instead of being terminated by it), the reaper re-reads the record immediately before dropping, and a heartbeat that has been failing for five minutes is logged as a warning by the owner rather than kept at debug. Unknown heartbeat information never authorises a drop, `jac db list` reports a condemned store as `silent scratch`, `jac db prune` names which signal condemned a database, and older clusters get the new columns in place on the next `jac db list`.
