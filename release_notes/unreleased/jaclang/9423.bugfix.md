# Fixed in native backend: UTF-8 codepoint semantics for string builtins

String builtins in the native backend treated UTF-8 byte offsets and byte
lengths as codepoint indices, producing corrupted results for any string
containing multibyte characters. Emitted `__jac_utf8_*` helpers now map
between byte buffers and codepoint indices, and consumers were converted:

- `len(str)`, `str[k]`, slicing (incl. step), and `for ch in s` are
  codepoint-based.
- `find`/`rfind`/`index`/`rindex`/`count` return codepoint indices and honor
  `start`/`end` region arguments (previously ignored).
- `startswith`/`endswith` region arguments are codepoint-based.
- `strip`/`lstrip`/`rstrip` charset membership and `center`/`ljust`/`rjust`/
  `zfill`/`expandtabs` width arithmetic are codepoint-based.
- `expandtabs` no longer relies on NUL termination (safe on sliced views).

`str(bytes)` behavior and `bytes` builtins are unchanged; `__jac_str_len`
remains a byte length for buffer sizing.
