- **Scale: `[scale.monitoring].enabled` decides whether the metrics stack deploys**: The configured switch did reach `KubernetesConfig.monitoring_enabled`, and was then discarded twice over: the observability path force-set the flag to `True` on the config it handed `MonitoringDeployer`, and the deployer gated its entire body on that same flag. Since the observability path is the deployer's only `deploy` caller (every other use is `destroy`, which is ungated), the gate could never evaluate false, so the switch decided nothing in either direction. A project that set `enabled = false` and turned logs on still got a full Prometheus and Grafana it had explicitly declined, and a project that set `enabled = true` with logs and tracing off got nothing at all, because the early return upstream never consulted the switch. The flag now reaches the deployer unchanged and scopes the stack it names, kube-state-metrics, node exporter and Prometheus, rather than the whole body; Tempo, Loki and Alloy keep their own flags, so turning monitoring off no longer takes logs and tracing down with it, and Grafana follows any backend that is enabled since it is the viewer for all three. The early return moved into a small predicate that consults all three sources, which also makes the decision testable without a cluster. Deployments that set `monitoring.enabled = false` alongside logs or tracing will stop receiving an unrequested Prometheus and Grafana on their next deploy.
