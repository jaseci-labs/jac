- **Breaking: read paths no longer take SERIALIZABLE predicate locks, and the provisioned Postgres is tuned for the isolation level jac uses**: `PgStore.begin()` defaulted to SERIALIZABLE and the session opened that transaction on the first read of a request, so every request ran its whole read volume under SSI. SERIALIZABLE takes one SIReadLock per row/page read and the predicate-lock pool is only `max_pred_locks_per_transaction * max_connections` entries, which the Kubernetes provisioner left at the stock 64 x 100. A fleet held 17,406 SIReadLocks across 20 connections, overflowed the ~6,400-entry pool, and then failed every statement with `53200 out of shared memory ... CreatePredicateLock` -- including the root read inside `JScaleExecutionContext()`, which `/healthz/live` and `/healthz/ready` both ran, so Kubernetes restarted pods that immediately hit the same error (#8050). Isolation now follows declared intent through a typed `TxnIsolation` enum: `Store.begin(serializable=..., read_only=...)` becomes `Store.begin(isolation=TxnIsolation.SERIALIZABLE | READ_COMMITTED | SNAPSHOT_READ_ONLY)`, and a session inside a declared read scope with nothing pending runs at `REPEATABLE READ READ ONLY`, which takes no predicate locks. Writes are unchanged: a unit of work still opens SERIALIZABLE, a read snapshot is restarted at SERIALIZABLE before any write is issued, and the read tier is READ ONLY at the server so a write that escapes that restart fails loudly instead of committing under-isolated. Scale context construction declares the read scope around its root probe, so health probes and requests that never run user code cost zero predicate locks. The `max_connections`, `max_pred_locks_per_transaction`, and `idle_in_transaction_session_timeout` settings now come from one place and reach the provisioned `postgres:18` StatefulSet as well as the embedded server, sized off the locks the fleet actually held: 1024 per transaction covers the measured ~870 per connection, and 1024 x 256 gives a 262,144-entry pool. `/healthz/live` and the legacy `/healthz` alias no longer build a database-backed context at all, `/healthz/ready` reports 503 when the database is unreachable so the pod leaves Endpoints without restarting, and an ordinary request whose context cannot be built reports 503 with `Retry-After` rather than a 500 traceback.
