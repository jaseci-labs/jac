- **Native: a tuple is iterable, and a boxed one no longer crashes codegen instead of demoting** (issue #8151): `for name in ('__init__.jac', '__init__.py', '__init__.pyi')` did not lower, while the same loop over a list literal did, so the idiomatic spelling cost a demotion wherever it appeared. A tuple lowers to an unboxed LLVM literal struct -- one field per element, each keeping its own type -- and `_box_value_tuple` puts that struct behind a pointer when it escapes; neither shape is a container, so the for-loop's iterable dispatch, which matches the collection against the list, dict, set, range, str and bytes runtime shapes, matched nothing and fell through to `E5092`. Worse, a *boxed* tuple is a pointer, so it took the dispatch's last-resort "an un-inferable pointer is a list of pointers" branch and called `__list_len_ptr` on a `{i64, i64, i64}*`: where the module had already emitted the `ptr` flavor's helpers, llvmlite's argument type check raised out of the pass and the compile aborted rather than demoting, and where it had not, the same site reported `E5092` -- so the diagnostic depended on what else the module happened to contain. A homogeneous tuple now materializes its fields into a sequence of the element flavor the list-literal path already picks (`i64` / `f64` / `ptr` / `jacval`, chosen by `_tuple_seq_flavor`, built by the existing `_emit_list_helpers`) and hands it to the same `_codegen_for_indexed(kind="list", ...)` loop, released at loop end like any list-literal loop; element coercion goes through `_coerce_type`, so it keeps the loud cross-flavor guard from #8052 rather than bitcasting around it. Ownership rides through: an owned element of a literal transfers its reference to the sequence, and an owned box is released once its fields have been read. The empty literal, the single-element literal, a tuple bound to a local, and a tuple returned from a call all take the same path.
- **Native: a tuple of mixed element storage refuses loudly rather than iterating boxed**: `for v in (1, 'ab', 3)` reports `E5092: Native lowering failed for for-loop iterable 'tuple with mixed element storage'` and the module demotes. This is deliberate and it is not the same call as the list literal's. The loop variable is a single slot, and `TypeEvaluator` types it from the tuple's *first* type argument (it specializes `tuple.__iter__`'s single `_T_co` against the tuple's args and keeps the first), so `v` is `int` and not `int | str`. Boxing the elements into tagged `jacval` slots would have compiled and run, and the body's `isinstance(v, str)` would then unbox `v` to `i64` and re-box it with the int tag before testing the tag -- always false, with nothing on stderr. The list spelling has no such problem, since `[1, 'ab', 3]` widens its element type to the union, and it keeps iterating boxed. Widening the loop-variable inference for a heterogeneous tuple would let this shape lower too, and is left as its own change.
- **Front end: `ModulePath.resolve_relative_path_list` iterates its `__init__` names as a tuple again**, retiring the list-literal rewrite 8ce175cdc5 (#8063) made purely to shed the seam.
