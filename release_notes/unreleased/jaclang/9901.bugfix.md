- **Fix: a rolled-back request no longer leaves its writes behind in the session**: the serving session recorded a row as stored (its hash and version) when a flush sent it, not when the transaction committed, and no rollback took that back. A serialization failure at `COMMIT` was therefore retried with versions the rollback had discarded and always ended as a `WriteConflict` on a row nobody else had changed; an edge whose write was flushed and then aborted stayed in memory with the rolled-back value, so the conflict re-run read it back and answered `200` without storing it or `409` although nothing was conflicting; and a conflict after an aborted attempt could delete a row that had only been evicted. The session now records flushed rows as pending and promotes them only after `COMMIT` returns, every rollback returns them to the unflushed set, `abort()` forgets every anchor the rolled-back transaction read or wrote, and deletes are replayed from an explicit record. A unit of work whose rollback also discarded another writer's rows (an enqueued outbox effect) is never committed in part: it raises the new `TransactionLost` conflict, which the request loop re-runs. Anchors loaded from the store are hashed once instead of twice.
