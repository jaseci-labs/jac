- **New: the autoscaler's view is reachable from the SDK, and documented**: `get_runtime_status` and `watch_scale_targets` existed on `Autoscaler` but nothing exported them, so an application asking why a workload sat at zero had to import internal module paths and wire three Kubernetes API clients by hand. `ScaleClient.autoscaler_status(app_name, namespace, service="")` and `ScaleClient.watch_autoscaler_transitions(app_name, namespace, ...)` now answer both, and `AutoscalerRuntimeStatus` and `AutoscalerTransition` join `jaclang.scale.sdk`'s exports. The caller passes an app or a service, never an autoscaler resource name: which resource is live depends on the scaling mode, and deriving it is the abstraction's job. The Kubernetes plugin reference gains the two sections the capability had none of: what each status field means and why `trigger_active` and `scaler_ready` are tri-state rather than boolean, that watch cardinality is the caller's responsibility because one call opens a bounded number of watches for one namespace and nothing is shared between callers, and that `observed_at` records when that observer saw a change rather than when it happened, so nothing here is durable history.
