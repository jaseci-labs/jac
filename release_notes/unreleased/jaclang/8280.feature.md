- **The native seal runs a worker process per root, which parallelises it and reclaims its memory at the same boundary**: sealing thirteen native roots was strictly sequential in one process, and that one process was carrying two costs at once. The roots are independent -- the single ordering edge is that `compiler/native_materialize.jac` is generated from unitree's layout -- so twelve of them waited on nothing but each other; and every materializer crossing strands that crossing's native tree, so one process accumulated all thirteen roots' stranded trees into a peak that killed hosted Linux runners outright (`#8279` bought the build time with a swapfile). The seal now supervises a pool of worker processes, one root each, orchestrated in Jac's own `flow`/`wait`: phase one seals unitree alone because the materializer is generated from what it produces, phase two fans the rest out `JAC_SEAL_JOBS` at a time. The threads only block on their children, so the concurrency and the reclaim both come from the process boundary -- each worker's stranded trees die when it exits, and no run accumulates more than the jobs in flight. The parent never compiles: it replays each worker's output in `NATIVE_SEAL_ROOTS` order so a pooled seal reads exactly like a sequential one, owns `SEAL_INDEX.json`, and keeps the sequential failure contract, where the first refusal drains the pool and the seal returns `None` with that worker's diagnostic printed verbatim. `JAC_SEAL_JOBS` sizes the pool and `JAC_SEAL_JOBS=1` is the escape back to the original in-process seal; with neither, the job count is derived from free memory over a measured per-root budget, capped by the core count. Reclaiming those trees *in* process still needs region- or ownership-based collection inside the sealing compiler, which is only possible once that compiler itself runs native; this is the boundary that was available today.
