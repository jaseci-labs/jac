- **Fix: a lazily spawned sibling service gets the configured boot health budget**: an inter-service import starts its peer with `jac start <mod>.jac --no-client` and waited on a hardcoded 15s health deadline, reading no config, while the orchestrated path already waits `boot_health_timeout` (60s) for the same operation and lets an operator raise it. A service whose cold start exceeded 15s could therefore never come up: each attempt was terminated partway through warming, so the child's log accumulated truncated compile runs and retrying never converged (measured at +2 modules banked per attempt against a 214-module cold start). The lazy spawn now honors the same `boot_health_timeout` key, and on that path the value is a stall budget rather than a wall clock: a child still writing to its log keeps the clock resetting, so a slow cold compile is not cut off, while a child that dies is still detected immediately. Failure now names which happened, reporting an exited child with its exit status and a stalled one with the budget it blew and the key to raise, instead of one flat "did not become healthy". `boot_health_timeout`, `boot_max_wait` and `health_monitor_interval` are read by the orchestrator and documented in the microservices guide but were never schema-declared; they are declared now. The spawn is also serialized per module: two concurrent first calls to one unregistered service both used to spawn a child, and since the port is derived from the module name both children raced onto the same port, so the loser died on bind, its caller's RPC failed spuriously, and one process could be left running with no handle to stop it. The second caller now waits and adopts the first one's service, and spawned siblings are tracked so `stop_sv_sibling` can terminate and reap exactly the process this runtime started; the health-cap failure path previously terminated its child without ever waiting on it.
