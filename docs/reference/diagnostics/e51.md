# E5114 to E5166: tail calls, C and Rust modules, the native library, programs, manifests and installed packages

These codes refuse what jac cannot build as written: a `return tail` that cannot reuse the
frame, a name that must be known when the program compiles, a C module or a Rust module that does
not build or does not bind, a C library named for another platform, a part of a Python module
that the native library leaves out, a file or a directory given to `jac build` or
`jac run` that is no program, and a value that `jac.toml` and the manifest jac writes from
it cannot both hold. Most C and Rust module codes need a project of several files,
so their entries show the file at fault instead of a whole program.

A C module is a directory with a `cmodule.toml`, and a Rust module a directory with a
`Cargo.toml`. A program imports either as it imports a Jac module (`import from counter {
counter_next }`). In the entries below, `counter/` is a C module and `adder/` a Rust module of the
project.

## E5114

```text
`return tail` cannot reuse the frame: {reason}
```

`return tail f(args);` promises that the call runs in the current function's frame, so a recursion
of any depth takes no stack. jac keeps the promise or refuses the program; it never lowers the
call as an ordinary one. `{reason}` says what stops it:

- `it is not in a function`: the statement is in a `with entry` block.
- `it does not call a Jac function directly`: the callee is a C function or a value.
- `a generator or coroutine cannot tail-call`.
- `a try, finally or with encloses it`: code would run after the call returns.
- `'f' takes 1 words and this function 2`: the callee's parameters do not take the same number of
  machine words as the caller's.
- `its result needs converting`: the callee returns a type the caller must convert to its own.
- `an argument lends a local of the caller`: an argument is `&x` or `&mut x` of a local.

```jac
# expect: E5114
def total(n: int, acc: int) -> int {
    if n == 0 {
        return acc;
    }
    try {
        return tail total(n - 1, acc + n);
    } finally {
        print("done");
    }
}
```

**Fix:** remove what `{reason}` names, or write a plain `return` when the frame need not be reused.
Here the `try` goes:

```jac
def total(n: int, acc: int) -> int {
    if n == 0 {
        return acc;
    }
    return tail total(n - 1, acc + n);
}

with entry {
    print(total(100000, 0));
}
```

```output
5000050000
```

See [Functions](../../language/functions.md).

## E5122

```text
jac needs {what} to be a string literal
```

A builtin that needs to know which attribute it reaches was given a name known only when the
program runs. `{what}` names the argument:

- `setattr()'s attribute name, unless its object is a class instance or an any,` and the same of
  `delattr()`: a computed name is accepted on an object of a class, or an `any`, whose
  attributes are looked up as the program runs; on a builtin value (a list, a str, a number)
  or a C struct it is not.
- `hasattr()'s attribute name, for a C struct,`: a C record's fields are fixed.

Python decides these when the line runs; here the attributes of a builtin value and of a C
struct are fixed when the program compiles.

```jac
# expect: E5122
def label(items: list[int], name: str) {
    setattr(items, name, 1);
}

with entry {
    label([1, 2], "tag");
}
```

**Fix:** write the name as a literal, or keep the attributes in an object of a class of your own,
whose attributes are found by name as the program runs:

```jac
class Labels {
    has tag: int = 0;
}

def label(target: Labels, name: str) {
    setattr(target, name, 1);
}

with entry {
    l = Labels();
    label(l, "tag");
    print(l.tag);
}
```

```output
1
```

## E5131

```text
the runtime module '{module}' binds the system library '{lib}', which only the platform layer (rt/pal) binds
```

A module of jac's own runtime (`rt/`) outside its platform layer (`rt/pal/`) binds a system
library: `c`, `pthread`, `dl`, `rt`, `libSystem`, `kernel32`, `ntdll`, `advapi32`, `bcrypt`,
`ws2_32` or a `wasi_*` host module. `{module}` is the runtime module and `{lib}` the library. It
arises only when changing jac's runtime; a program's own modules bind these libraries freely.

**Fix:** move the binding into a module under `rt/pal/` and call it from there.

## E5132

```text
the C module '{module}': its cmodule.toml {reason}
```

The manifest of a C module cannot be read. `{module}` is the C module and `{reason}` what is wrong
with its `cmodule.toml`: it is not valid TOML, it has an unknown key, a key holds the wrong kind of
value (`has a 'sources' that is not a list of strings`), or it names a file or directory that does
not exist. It arises from a manifest such as this one, whose `colour` is no key:

```toml
headers = ["counter.h"]
colour = "blue"
```

**Fix:** correct the manifest as `{reason}` says. The keys are `headers`, `sources`, `include`,
`defines`, `cflags`, `cxxflags`, `libs`, `frameworks`, `archives`, `whole_archives`, `shared`,
`prebuilt_shared`, and at the top only `inline`, `export` and the `[target.<os>]` tables; a
`[files."<source>"]` table takes `include`, `defines` and `cflags`. See
[C modules](../../interop/c-modules.md).

## E5133

```text
'{name}' of the C module '{module}' cannot be bound: {reason}
```

A program imports a name that the C module's headers declare, but in a form Jac cannot bind, so
the module's interface leaves it out. `{name}` is the name, `{module}` the C module, and `{reason}`
why: a `static inline` function defines no symbol, and a union, a bit-field or a parameter of an
unsupported C type has no Jac form. It arises when `counter/counter.h` declares
`static inline int counter_next(void) { return 1; }` and the program imports `counter_next`.

**Fix:** give the C module a function Jac can call: declare `int counter_next(void);` in the header
and define it in one of the module's `sources`, or wrap the inline function or the union in a
plain function that takes and returns C scalars, pointers or records.

## E5134

```text
the interface headers of the C module '{module}' do not compile
```

Clang cannot compile the headers that a C module's `cmodule.toml` lists under `headers`. `{module}`
is the C module; Clang's own errors are printed above this one. It arises from a header with a
syntax error, such as `int counter_next(void)` with no `;`, or one that includes a file not found
in the module's `include` directories.

**Fix:** correct the header as Clang's errors say, or add the directory it includes from to
`include`.

## E5135

```text
the C file {path} does not compile
```

A source file of a C module does not compile. `{path}` is the file; Clang's errors are printed
above this one. It is reported by `jac build`, which compiles the sources, and not by
`jac check`, which reads only the headers.

**Fix:** correct the C source as Clang's errors say.

## E5136

```text
the C module '{module}' is wired {what}, but a C module takes only other C modules' interfaces or a Rust module, whole
```

A wire in `archwire.jac` brings into a C module something it cannot take. `{module}` is the C
module and `{what}` what the wire brings: `from the Jac module 'helper'`, `names from the C module
'shapes'` or `names from the Rust module 'adder'`. A C module's sources include another C module's
headers whole, and call a Rust module's `extern "C"` functions by name; they cannot call Jac. It
arises from a wire such as `helper ++> counter;` where `helper` is a Jac module.

**Fix:** wire only a C module or a Rust module into a C module, and without a list of names:
`shapes ++> counter;`. See [archwire](../../apps/archwire.md).

## E5137

```text
the Rust module '{module}': cargo says: {reason}
```

cargo cannot work out what to build for a Rust module. `{module}` is the module and `{reason}` is
cargo's own message: the `Cargo.toml` cannot be parsed, a dependency cannot be resolved, or the
package has no library to build. It arises, for example, from `edition = "2077"` in the
`Cargo.toml`.

**Fix:** correct the `Cargo.toml` as cargo says. `jac cargo metadata --format-version 1` in
the module's directory shows cargo's message in full.

## E5138

```text
'{name}' of the Rust module '{module}' cannot be bound: {reason}
```

A program imports a name that a Rust module declares, but in a form Jac cannot bind. `{name}` is
the name, `{module}` the Rust module, and `{reason}` why: most often a parameter or result has a
Rust type no C function has (a tuple, a `String`, a slice), or a function pointer that is not
`extern "C"`. It arises from `pub extern "C" fn add(a: i64, b: (i64, i64)) -> i64` imported as
`import from adder { add }`.

**Fix:** give the function a C signature, `#[unsafe(no_mangle)] pub extern "C"` with integers,
floats, raw pointers and `#[repr(C)]` records, and convert to and from Rust's own types inside it.
See [Rust modules](../../interop/rust-modules.md).

## E5139

```text
the interface of the Rust module '{module}' cannot be read
```

jac reads a Rust module's interface with rustdoc, and rustdoc could not read it, or the
module's compiled unit could not be made. `{module}` is the Rust module; the tool's output is
printed above this one. It arises when rustdoc fails on a crate that rustc compiles, or when the
crates' build order has a cycle.

**Fix:** run `jac rustdoc` on the crate to see the failure, and correct the crate.

## E5140

```text
the Rust crate {crate} does not compile
```

A crate of a Rust module, the module's own or one of its dependencies, does not compile. `{crate}`
is the crate's name; rustc's errors are printed above this one. It arises from Rust code with an
error, such as `a + missing` where nothing is named `missing`.

**Fix:** correct the crate as rustc's errors say.

## E5141

```text
the Rust module '{module}' is wired {what}: a crate takes names from a Jac module, and a C module whole
```

A wire in `archwire.jac` brings into a Rust module something it cannot take. `{module}` is the
Rust module and `{what}` what the wire brings: `the whole Jac module 'helper'`, `names from the C
module 'counter'` or `from the Rust module 'other'`. A crate calls a Jac module's functions by the
names a wire lists, and a C module's functions through its whole interface. It arises from a wire
such as `helper ++> adder;` with no names.

**Fix:** list the Jac functions the crate calls (`helper ++> adder { helper_value }`), wire a C
module without names (`counter ++> adder;`), and never wire one Rust module into another. See
[archwire](../../apps/archwire.md).

## E5142

```text
'{what}' is part of Python's {module} module but not of the native one: {why}; {instead}. CPython's {pymodule} is reachable explicitly: importlib.import_module("{pyname}")
```

The program uses a name of a standard library module that jac's native module of the same name
leaves out on purpose. `{what}` is the name, `{module}` and `{pymodule}` the module, `{pyname}` its
name for `importlib`, `{why}` why the native module has no such name, and `{instead}` what to write
in Jac. Python's habits lead here: `collections.namedtuple`, for one, makes a class while the
program runs, and a Jac class is declared.

```jac
# expect: E5142
import from collections { namedtuple }

with entry {
    Point = namedtuple("Point", ["x", "y"]);
}
```

**Fix:** do what `{instead}` says. For `namedtuple`, declare an `obj`:

```jac
obj Point {
    has x: int,
        y: int;
}

with entry {
    p = Point(x=1, y=2);
    print(p.x + p.y);
}
```

```output
3
```

When CPython's own module is what the program needs, take it with
`importlib.import_module("collections")`, which gives CPython's module, its values Python
objects.
See [the standard library](../../library/index.md).

## E5143

```text
'{module}' is a module of Python's {package} package but not of the native one. CPython's {pymodule} is reachable explicitly: importlib.import_module("{pyname}")
```

The program imports a submodule of a standard library package that jac's native package does
not have. `{module}`, `{pymodule}` and `{pyname}` are the dotted submodule, and `{package}` its
package.

```jac
# expect: E5143
import json.tool;

with entry {
    print(1);
}
```

**Fix:** import the package and use what the native one has (`import json;` and `json.dumps`), or
take CPython's submodule with `importlib.import_module("json.tool")`. See
[the standard library](../../library/index.md).

## E5144

```text
the crates of the Rust module '{module}' do not link together
```

The crates of a Rust module compiled, but rustc cannot link them into the one static library the
program takes. `{module}` is the Rust module; rustc's errors are printed above this one. It arises
when rustc refuses to link the crates of the module's dependency graph, after each of them compiled
on its own.

**Fix:** correct the conflict that rustc's errors name, in the module's `Cargo.toml` or its
dependencies.

## E5145

```text
'{name}' is declared otherwise than the headers of the C module '{module}' declare it: {header}
```

A module binds a function of a C module by declaring it itself (`import from counter { def
counter_next -> i32; }`), and the declaration disagrees with the C module's headers: a different
number of parameters, a parameter or the result of another type or passed another way, or a
variadic mismatch. `{name}` is the function, `{module}` the C module and `{header}` the headers'
signature, such as `(i32) -> i32`. It arises when `counter.h` declares
`int counter_next(int step);` and the declaration takes no parameter.

**Fix:** declare it as `{header}` says: `def counter_next(step: i32) -> i32;`, or import the name
without declaring it (`import from counter { counter_next }`) and take the headers' declaration.

## E5146

```text
the Rust modules '{first}' and '{second}' both give the program '{symbol}', which {user} calls by name: a symbol has one provider
```

Two Rust modules export a function or static of the same symbol name, and the program needs that
symbol by name. `{first}` and `{second}` are the modules, `{symbol}` the name, and `{user}` who
calls it: the program's Jac, or a C module the crates are wired into. Each Rust module's other
symbols are private to it, so only a symbol the program reaches by name must be unique. It is
reported by `jac build`, and arises when `adder` and `summer` both define
`#[unsafe(no_mangle)] pub extern "C" fn add` and the program imports `add` from each, even under
an alias.

**Fix:** give the functions different symbol names in Rust (`summer_add`), or import the symbol
from one module only.

## E5147

```text
the system library '{lib}', which a C module or a Rust crate links, has no stub in the toolchain's macOS system root (lib/libc/darwin/usr/lib)
```

On macOS, a C module's `libs` or a Rust crate's build names a system library that the toolchain's
copy of the macOS system root does not describe, so the program cannot link against it. `{lib}` is
the library. It is reported by `jac build` for a macOS target, and arises from
`libs = ["nosuchlib"]` in a `cmodule.toml`.

**Fix:** correct the library's name (`libs = ["z"]` for `libz`), or, for a library that is not part
of macOS, give the module the library itself as an archive (`archives = ["lib/libfoo.a"]`).

## E5148

```text
the C library file '{file}' is {platform}'s, and this program is built for {target}: a module variant for each platform names its own library (X.linux.jac, X.darwin.jac, X.windows.jac)
```

An `import from "<file>"` names a C library by a file of another platform than the one the program
is built for. `{file}` is the file as written, `{platform}` the platform its name belongs to
(`libz.so.1` is Linux's, `libz.dylib` macOS's, `zlib1.dll` Windows's) and `{target}` the build's.

```jac
# expect: E5148
import from "zlib1.dll" {
    def zlibVersion -> str;
}

with entry {
    print(zlibVersion());
}
```

**Fix:** name the library by its name when the platforms share one (`import from z { ... }`), or
give the module a variant for each platform (`zlib.windows.jac` binding `"zlib1.dll"`,
`zlib.linux.jac` binding `"libz.so.1"`). See [C libraries](../../interop/c-libraries.md).

## E5149

```text
'{name}' is not a C library file's name: a quoted C library is its file (lib<name>.so, lib<name>.so.<version>, lib<name>.dylib or <name>.dll), and an unquoted one its name
```

An `import from` names a C library in quotes, and the quoted text is not a library file's name.
`{name}` is the text. Quotes mean the exact file; a library's plain name is written without them.

```jac
# expect: E5149
import from "zlib" {
    def zlibVersion -> str;
}

with entry {
    print(zlibVersion());
}
```

**Fix:** drop the quotes to name the library (`z` is zlib on every platform):

```jac
import from z {
    def zlibVersion -> str;
}

with entry {
    print(len(zlibVersion()) > 0);
}
```

```output
True
```

See [C libraries](../../interop/c-libraries.md).

## E5150

```text
'{path}' is no program jac knows: a program's file is known by its extension, one of {extensions}
```

`jac build` or `jac run` is given a file whose extension names no kind of program. `{path}`
is the file as given and `{extensions}` the extensions a program's file is known by: `.jac`, a C
or C++ file's (`.c`, `.cc`, `.cpp`), a Rust file's (`.rs`), a Python file's (`.py`) and a
JavaScript or TypeScript file's (`.js`, `.mjs`, `.cjs`, `.ts`). The extension is read before the
file is looked for, so a file that is not there is refused by its extension first.

```text
$ jac build notes.txt -o notes
error[E5150]: 'notes.txt' is no program jac knows: a program's file is known by its extension, one of .jac, .c, .cc, .cpp, .rs, .py, .js, .mjs, .cjs, .ts
```

**Fix:** name the program's file (`jac build main.jac -o notes`), or the directory that holds
its manifest.

## E5151

```text
the directory '{dir}' holds no manifest a program is known by, one of {manifests}
```

`jac build` or `jac run` is given a directory, or none and so the directory it runs in, and
the directory holds none of the manifests a program is known by. `{dir}` is the directory as given
(`.` for the current one) and `{manifests}` the manifests, in the order they are looked for:
`archwire.jac`, `jac.toml`, `Cargo.toml`, `cmodule.toml`, `pyproject.toml` and `package.json`.

```text
$ jac run
error[E5151]: the directory '.' holds no manifest a program is known by, one of archwire.jac, jac.toml, Cargo.toml, cmodule.toml, pyproject.toml, package.json
```

**Fix:** run the command from the project's root, name the project's directory, or name the
program's file (`jac run main.jac`).

## E5152

```text
the Jac project '{dir}' has no {main}, the program it is
```

`jac build` or `jac run` is given a directory whose manifest is a `jac.toml`, a Jac project,
and the project has no main module. `{dir}` is the project's directory and `{main}` the module a
Jac project's program is, `main.jac`.

```text
$ jac run noprog
error[E5152]: the Jac project 'noprog' has no main.jac, the program it is
```

**Fix:** write the project's `main.jac`, or name the module that is the program
(`jac run noprog/app.jac`).

## E5153

```text
'{path}' is one of the runtime's internal modules, which jac loads into a program and is not a program itself
```

`jac build`, `jac check` or `jac test` is given one of the runtime's internal modules as
the program's main module. `{path}` is the file named. The internal modules are the ones jac
itself loads into a program from the `rt` directory beside it: `core`, `methods`, `fmath`, `kmath`,
`threads`, `py` and the platform layer `pal`. None is a program of its own. The library's modules
and the Python and Node hosts under `rt` are not internal, and this code is not about them.

```text
$ jac check rt/core.jac
rt/core.jac:1:1: error[E5153]: 'rt/core.jac' is one of the runtime's internal modules, which jac loads into a program and is not a program itself
```

**Fix:** check a program instead. `jac check <main.jac>` checks the runtime's modules that the
program loads along with it.

## E5154

```text
'{module}' is Python's, and this program is built into one executable with others: a program using Python carries its interpreter, and is built alone
```

A program given to `jac build` with other programs, for one executable that holds them all,
imports a module that is Python's. `{module}` is the module. A program using Python is built with
CPython linked in, and with its standard library beside it, which the other programs of the
executable would each carry too.

```text
$ jac build count.jac report.jac -o tools
report.jac:1:8: error[E5154]: 'ast' is Python's, and this program is built into one executable with others: a program using Python carries its interpreter, and is built alone
```

**Fix:** build that program alone (`jac build report.jac -o report`), and the others together.
See [Several programs in one executable](../../toolchain/build.md#several-programs-in-one-executable).

## E5155

```text
jac.toml's {key} is {what}, which {file} has no value for
```

An npm tree of `jac.toml` holds a value that JSON has none for, so jac cannot write the tree's
`package.json`. `{key}` is the key, `{what}` the value's kind and `{file}` the file that would be
written. TOML's dates and times, and the floats `inf` and `nan`, are the values JSON lacks.

```toml
[npm.web]
private = true
released = 2026-01-01
```

```text
$ jac install
jac.toml: error[E5155]: jac.toml's npm.web.released is a date, which eco/web/package.json has no value for
```

**Fix:** write the value as `package.json` would hold it, a string: `released = "2026-01-01"`.

## E5156

```text
{key} {why}: {file} cannot hold it, so nothing of what was written here is taken
```

A manifest another tool wrote holds a value TOML has none for, so `jac.toml` or `jac.lock` cannot
take it. `{key}` is the key as it would be in `{file}`, and `{why}` says what it holds. JSON's
`null` is the value TOML lacks. The diagnostic names the manifest. Nothing of it is taken: neither
`jac.toml` nor `jac.lock` changes, and `jac absorb` moves no file.

```text
$ jac npm pkg set 'overrides.left-pad=null' --json
eco/web/package.json: error[E5156]: npm.web.overrides.left-pad is null, which TOML has no value for: jac.toml cannot hold it, so nothing of what was written here is taken
```

**Fix:** take the `null` out of the manifest, or say what it stood for another way (npm reads an
absent key as it reads a `null`). The next command writes the tree's files from `jac.toml` again,
so a change that was refused is gone from them.

## E5157

```text
{table} of {file} is written in a form jac does not rewrite: write it as a table under its own header
```

jac has a table of `jac.toml` or `jac.lock` to replace, and the file writes that table in a
form it will not edit: an inline table (`web = { ... }`), or dotted keys under another header.
`{table}` is the table and `{file}` the file. jac replaces a table that stands under its own
header, and leaves the rest of the file, its comments with it, as it was.

```toml
[npm]
web = { private = true }
```

```text
$ jac install --npm nanoid
jac.toml: error[E5157]: [npm.web] of jac.toml is written in a form jac does not rewrite: write it as a table under its own header
```

**Fix:** give the table its header:

```toml
[npm.web]
private = true
```

## E5158

```text
jac.toml's {key} is not {what}
```

`jac.toml`'s `npm` is not a table of trees, or one of its entries is not a tree. `{key}` is the key
and `{what}` what it must be. A tree is a table, `[npm.<tree>]`, and its name is the directory it
is written to under `eco/`: letters, digits, `-` and `_`.

```toml
[npm]
web = "latest"
```

```text
$ jac install
jac.toml: error[E5158]: jac.toml's npm.web is not a package tree, [npm.<tree>], named in letters, digits, - and _
```

**Fix:** make it a table holding what the tree's `package.json` holds:
`[npm.web.dependencies]` with a line for each package.

The same code refuses any other table of `jac.toml` that is not in the form it has: an entry of
`[packages]` that is no source, a key of an abstraction's table that is neither
`plugin` nor a plugin's table, and what a space's `ui` and `bundler` tables may not hold. Each is
reported at its line. For a space's plugins it is:

| `jac.toml` has | Why it is refused |
|---|---|
| `ui = "preact"` or `bundler = "vite"` under `[spaces.<space>]` | The plugin is named in a table: `[spaces.<space>.ui]` `plugin = "preact"` |
| `bundler_config` under `[spaces.<space>]` | A bundler's configuration is a setting of its plugin: `[spaces.<space>.bundler.vite]` `config` |
| `[spaces.<space>.ui.solid]` in a space built with `preact` | `ui` and `bundler` are picked as a space is built, so a space has one plugin of each and lists no other |
| `[spaces.<space>.bundler.vite]` `minify = true` | `minify` is not among the settings the plugin's own `jac.toml` lists |

```toml
[spaces.site]
ui = "preact"
```

```text
$ jac build site
jac.toml:5:1: error[E5158]: jac.toml's [spaces.site] ui is not a value: `[spaces.site.ui]` is a table that names a plugin for `ui`, `plugin = "<name>"`
```

**Fix:** write the table the message names
([UI plugins and bundlers](../../apps/ui-bindings.md#choosing-a-spaces-plugins)).

## E5159

```text
npm tree '{tree}' has workspaces: a tree is one package, and another package is another tree, [npm.<tree>]
```

An npm tree declares `workspaces`, in `jac.toml` or in the `package.json` a tool wrote or
`jac absorb` was given. `{tree}` is the tree. A tree is one package with one lock. A project of
several packages has a tree for each, and each space names its own.

```toml
[npm.web]
workspaces = ["mobile"]
```

```text
$ jac install
jac.toml: error[E5159]: npm tree 'web' has workspaces: a tree is one package, and another package is another tree, [npm.<tree>]
```

**Fix:** take `workspaces` out, and give each member package a tree of its own
(`jac absorb mobile` takes a directory's `package.json` in as one).

## E5160

```text
the packages of npm tree '{tree}' are not installed as jac.toml and jac.lock say: run `jac install`
```

A build needs an npm tree's packages, and what is installed in `eco/<tree>/node_modules` was not
installed from the tree as `jac.toml` and `jac.lock` now have it. `{tree}` is the tree. Either it
was never installed (a fresh clone), or `jac.toml` or `jac.lock` changed since. It is reported
where a module first imports from npm, or of the app whose space is bundled.

```text
$ jac build web
web.jac:1:1: error[E5160]: the packages of npm tree 'web' are not installed as jac.toml and jac.lock say: run `jac install`
```

**Fix:** `jac install`. It runs npm only for a tree that is not as pinned, and
`jac install --frozen` installs exactly what `jac.lock` pins.

## E5161

```text
the {kind} '{name}' is not installed as {package} asks, {asked}: {remedy}
```

A package is not in the project's `eco/jac/<name>` as a declaration asks. `{kind}` is `package`,
`{name}` the package, `{package}` the package whose `jac.toml` declares it, `{asked}` what it asks
for and `{remedy}` what is missing or what to run. It is reported at the package's line of the
`jac.toml` that declares it.

A package declared by its version is an [installed](../../toolchain/packages.md#installed-packages)
one, which a package manager puts there:

```toml
[packages]
grid = "1.2"
```

```text
$ jac build main.jac
jac.toml:5:1: error[E5161]: the package 'grid' is not installed as the project asks, version 1.2 or later, below 2.0.0: nothing is at 'eco/jac/grid'
```

**Fix:** install the package into the project's `eco/jac/grid`, with whatever installs the
project's packages.

A package declared by a repository is fetched by jac. It is this error when it was never
fetched (a fresh clone), or `jac.toml` now asks for another repository or revision:

```toml
[packages]
units = { git = "https://example.com/units.git", rev = "v1.2.0" }
```

```text
$ jac build main.jac
jac.toml:5:1: error[E5161]: the package 'units' is not installed as the project asks, https://example.com/units.git at v1.2.0: run `jac install`
```

**Fix:** `jac install`, which fetches it and pins its commit in `jac.lock`.
`jac install --frozen` fetches exactly the commit pinned.

## E5162

```text
the npm package '{name}' is asked for at {range} by {asker}, and at {other} by {another}: a tree holds one, so make them agree
```

An npm tree would hold one npm package at two ranges: the project's own `[npm.<tree>]` asks for
one, and a library or a plugin the project declares for another, or two of those do. `{name}` is
the npm package, `{range}` and `{asker}` one range and who asks for it, `{other}` and `{another}`
the other. A tree is one `package.json`, which names a package once.

```toml
[packages]
shapes = { path = "../shapes" }

[npm.web.dependencies]
leftpad = "^2.0.0"
```

reports, where `shapes` has `leftpad = "^1.0.0"` in an `[npm.<tree>.dependencies]` of its own:

```text
jac.toml: error[E5162]: the npm package 'leftpad' is asked for at ^2.0.0 by [npm.web], and at ^1.0.0 by a package the project declares: a tree holds one, so make them agree
```

**Fix:** write one range in both.

## E5163

```text
the package in '{dir}' has no record of what installed it: '{record}' {problem}
```

A package declared by its version is in the project's `eco/jac/<name>`, and nothing says what put
it there. `{dir}` is the package's directory, `{record}` the record that belongs beside it,
`eco/jac/<name>.json`, and `{problem}` what is wrong with it: it is not there, or it is not a JSON
object that names its `installer` and its `format`. Every
[installed package](../../toolchain/packages.md#installed-packages) has a record, so that each is
some installer's to replace and to remove, and no two installers take one for theirs.

```toml
[packages]
grid = "1.2"
```

reports, where `eco/jac/grid` was copied in by hand:

```text
jac.toml:5:1: error[E5163]: the package in 'eco/jac/grid' has no record of what installed it: 'eco/jac/grid.json' is not there. An installer writes one beside each package it installs, and a package kept by hand is declared by `path`
```

**Fix:** install the package with what installs the project's packages. To use a directory you
keep yourself, declare it by where it is: `grid = { path = "../grid" }`.

## E5164

```text
'{file}' is of format {found}, and this jac reads format {format}: {remedy}
```

A file jac reads beside a project's packages is in a format this jac does not read.
`{file}` is the file, `{found}` the format it says it is, `{format}` the one this jac reads
and `{remedy}` what to do. A record's format is its `format` key, and `jac.lock`'s its `version`.
A format changes as a whole, under a new number: jac reads one, and never guesses at another.

```text
jac.toml:5:1: error[E5164]: 'eco/jac/grid.json' is of format 2, and this jac reads format 1: install the package again with 'jacpm', in a version that writes this format
```

For `jac.lock`:

```text
$ jac install
jac.lock: error[E5164]: 'jac.lock' is of format 1, and this jac reads format 2: delete it and run `jac install`, which pins what is installed now
```

**Fix:** what `{remedy}` says: install the package again with an installer that writes the format
this jac reads, or build with the jac the installer was made for. Delete a `jac.lock` of
another format and run `jac install`.

## E5165

```text
'{dir}' holds a package that {who}, and {package} asks for {asked}: `jac install` replaces only what it fetched itself, so remove the package with what installed it
```

`jac.toml` declares a package by a repository, which `jac install` fetches into
`eco/jac/<name>`, and a package is there already that jac did not fetch. `{dir}` is that
directory, `{who}` what its record says installed it, or that no record says jac did,
`{package}` the package whose declaration this is and `{asked}` the repository and revision it
asks for. An installer touches only the packages whose record names it.

```text
$ jac install
jac.toml: error[E5165]: 'eco/jac/units' holds a package that 'jacpm' installed, and the project asks for https://example.com/units.git at v1.2.0: `jac install` replaces only what it fetched itself, so remove the package with what installed it
```

**Fix:** remove the package with the installer that put it there, then `jac install`. Or
declare it as that installer provides it, by its version.

## E5166

```text
the {kind} '{name}' in '{dir}' is not what jac.lock pins, {pinned}: {remedy}
```

`jac install` finds an installed package that is not the one `jac.lock` pins
([The lock](../../toolchain/packages.md#the-lock)). `{kind}` and `{name}` are the package, `{dir}`
its directory, `{pinned}` what the lock pins and `{remedy}` what to do. It is one of:

- the package's files are not the ones pinned, though its version and where it came from are:
  the same version from the same place is the same files, so something changed them;
- under `--frozen`, its version or what its record says of where it came from is not what is
  pinned;
- a commit `jac install` fetched again holds other files than when it was pinned.

```text
$ jac install --frozen
jac.toml: error[E5166]: the library 'cells' in 'eco/jac/cells' is not what jac.lock pins, version 0.3.2, which 'jacpm' installed: its files have changed since it was pinned, so install it again with 'jacpm'
```

**Fix:** install the package again with what installed it. Where the change is meant (another
version was installed), `jac install` without `--frozen` pins what is there.
