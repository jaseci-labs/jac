# E1110 to E1147: operators, walkers, numbers and imports

E1110 to E1128 are reported for operators and numbers whose operand types do not go together, and
for `spawn` and abilities given the wrong kind of thing. E1134 to E1147 are about where names come
from: an import that names nothing, and the wires of an `archwire.jac`, which state the imports
between the modules of a project.

## E1110

```text
'{op}' is not supported between {left} and {right}
```

A binary operator or a comparison is applied to two types that it does not combine. `{op}` is the
operator, `{left}` and `{right}` the operand types. Python raises `TypeError` for these when the
line runs; here the program is refused.

```jac
# expect: E1110
with entry {
    print("total: " + 3);
}
```

**Fix:** convert one side by name (`"total: " + str(3)`), or format the value into the string
(`f"total: {3}"`). A class takes part in an operator by defining its method (`__add__` for `+`).
See [Operators](../../language/operators.md).

`sorted`, `min`, `max` and `list.sort` compare their items with `<` (`max` with `>`), so each is
this code too when the items' type has no order, reported at the call:

```jac
# expect: E1110 x2
obj Item {
    has n: int = 0;
}

with entry {
    items = [Item(n=2), Item(n=1)];
    print(sorted(items), max(items));
}
```

**Fix:** give the class a `__lt__` taking its own type, or sort by a key:
`sorted(items, key=lambda (i: Item) -> int { return i.n; })`. See
[Special methods](../../language/methods-special.md).

## E1111

```text
'{op}' needs a container on the right, found {type}
```

The right operand of `in` or `not in` is not something that holds items. `{op}` is the operator and
`{type}` the right operand's type. A list, tuple, set, dict, str, bytes, range and an object whose
class defines `__contains__` can be tested for membership.

```jac
# expect: E1111
with entry {
    print(1 in 5);
}
```

**Fix:** put a container on the right (`1 in [5]`), or compare with `==` if one value was meant.

## E1114

```text
only a walker can be spawned, found {type}
```

`spawn` is given something that is not a walker. `{type}` is its type. `node spawn W()` and
`W() spawn node` both start a walker on a node; an `obj` instance cannot be spawned.

```jac
# expect: E1114
node City {}

obj Tour {}

with entry {
    c = City();
    c spawn Tour();
}
```

**Fix:** declare the type with `walker` instead of `obj`: `walker Tour {}`. See
[Walkers](../../language/walkers.md).

## E1115

```text
a walker spawns on a node, found {type}
```

The place a walker is spawned on is not a node. `{type}` is the type of the value written there.

```jac
# expect: E1115
walker Tour {}

with entry {
    5 spawn Tour();
}
```

**Fix:** spawn on a node, or on `root`:

```jac
walker Tour {
    can start with entry {
        print("started");
    }
}

with entry {
    root spawn Tour();
}
```

```output
started
```

See [Walkers](../../language/walkers.md) and [root](../../language/root.md).

## E1116

```text
a walker's ability is triggered by a node or an edge type, and {trigger} is {what}
```

A walker's ability names a trigger that is not a node or an edge type, so it could never fire: a
walker is only ever at nodes and edges. `{trigger}` is the name written and `{what}` what it is (`a
walker`, `an obj`); for something that is no name at all (a value, a string), they read `its
trigger` and `no archetype's name`.

```jac
# expect: E1116 x2
node City {}

walker Guide {}

walker Tour {
    can go with 5 entry {
        print("here");
    }

    can follow with Guide entry {
        print("there");
    }
}
```

**Fix:** name a node or an edge type (`can go with City entry`), a union of them (`with City |
Town entry`), or leave the trigger out to run once as the walk starts (`can go with entry`). See
[Abilities](../../language/abilities.md).

## E1117

```text
the ability of a node or an edge is triggered by a walker type, and {trigger} is {what}
```

An ability of a node or an edge names a trigger that is not a walker type, so it could never fire:
what arrives at a node is a walker. `{trigger}` and `{what}` are as in E1116.

```jac
# expect: E1117
node City {}

node Town {
    can greet with City entry {
        print("hello");
    }
}
```

**Fix:** name the walker type the ability runs for (`can greet with Tour entry`), or leave the
trigger out to run for every walker. To run when a walker is at a `City`, put the ability in the
walker: `can at_city with City entry`. See [Abilities](../../language/abilities.md).

## E1119

```text
cannot infer the type of parameter '{name}'; annotate it
```

A lambda's parameter has no type annotation and nothing else gives it one. `{name}` is the
parameter. A lambda's parameter types come from its annotations, or from the `Callable` type the
lambda is assigned or passed to.

```jac
# expect: E1119
with entry {
    double = lambda (x) { return x * 2; };
    print(double(2));
}
```

**Fix:** annotate the parameter, or declare the type the lambda is stored as:

```jac
with entry {
    double = lambda (x: int) -> int { return x * 2; };
    triple: Callable[[int], int] = lambda (x) { return x * 3; };
    print(double(2), triple(2));
}
```

```output
4 6
```

See [Functions](../../language/functions.md).

## E1126

```text
{value} does not fit in {type}
```

A number known when the program compiles is outside the range of the type it is used as: a
literal, or a compile-time int (a `comptime` global, a `comptime` function's result) where it is
converted to a sized int, as an `int` given to a C function's `i32` parameter is. `{value}` is the
number and `{type}` the type. An `int` is 64 bits, so a literal past its range is refused too,
and a negative literal fits no unsigned type.

```jac
# expect: E1126
with entry {
    small: u8 = 300;
    print(small);
}
```

**Fix:** use a type wide enough for the value (`small: u16 = 300;`; a `u64` holds literals up to
18446744073709551615). See [Numbers](../../language/numbers.md).

## E1128

```text
'{op}' mixes {left} and {right}; convert one side
```

An operation has two number types of which neither can hold every value of the other, so no result
type is safe to pick. `{op}` is the operator (or the function, as `sum()`), `{left}` and `{right}`
the two types. Two different float types never mix; two int types mix only when one widens to the
other, so `u8` with `i16` is fine and `u8` with `i8` is not.

```jac
# expect: E1128
with entry {
    a: f32 = 1.5;
    b: float = 2.5;
    print(a + b);
}
```

**Fix:** convert one side by name to the type the result should have: `float(a) + b` or
`a + f32(b)`. See [Numbers](../../language/numbers.md).

## E1134

```text
relative import '{module}' names no module
```

A relative import (`import from .x { ... }`) finds no module at that place. `{module}` is the path
as written, with its leading dots. One dot is the importing file's directory, two dots the
directory above it.

```jac
# expect: E1134
import from .nowhere { thing }

with entry {
    print(thing);
}
```

**Fix:** correct the name or the number of dots so that the path leads to a `.jac` file or a
package directory. See [Modules](../../language/modules.md).

## E1136

```text
the {side} side of this connect is {actual}, and edge '{edge}' declares its {end} as {declared}
```

A connect joins nodes that the edge's declared endpoints do not name. `{side}` is `left` or
`right`, `{actual}` the operand's node type, `{edge}` the edge type, `{end}` is `source` or
`destination`, and `{declared}` the node types that endpoint names. `a +>:E:+> b` connects one of
`E`'s source types to one of its destination types; `a <+:E:<+ b` connects `b` to `a`. A typed
reference along the edge has the endpoint's type (`[a ->:Wrote:->]` is a `list[Book]`), so an edge
joins only what it declares.

```jac
# expect: E1136 x2
node Author {
    has name: str;
}

node Book {
    has title: str;
}

edge Wrote: Author --> Book {}

with entry {
    ann = Author(name="ann");
    book = Book(title="book");
    book +>:Wrote:+> ann;
}
```

**Fix:** connect the nodes the way the edge points (`ann +>:Wrote:+> book`), or declare the
endpoints the edge is meant to join: a union (`edge Wrote: Author | Editor --> Book {}`) names
several. An operand whose class is known only as the program runs (a base node type, a union) is
checked as it connects, and raises `TypeError: expected Author, found Shelf`. See
[Edges](../../language/edges.md).

## E1141

```text
'{module}' is not a module under this archwire.jac, so it cannot be a wire's provider
```

A wire in `archwire.jac` names a provider that is not a module in the directory tree the file
governs. `{module}` is the provider as written. A wire `provider ++> consumer { names }` imports
`names` from `provider` into `consumer`. It arises from a project's `archwire.jac`, for example
`utils ++> main { now }` where the module's file is `util.jac`.

**Fix:** name the module by its path from the `archwire.jac`'s directory, with dots between
directories (`lib.use` for `lib/use.jac`). See [archwire](../../apps/archwire.md).

## E1142

```text
'{module}' cannot be a wire's consumer: {detail}
```

A wire in `archwire.jac` names a consumer that cannot take the import. `{module}` is the consumer
and `{detail}` says why:

- the wire names the same consumer twice (`util ++> main | main { now }`);
- the consumer is a package directory with no `__init__` module to receive the import;
- the consumer is neither a Jac module nor a C module, nor a file in another language that a `-->` wire
  declares an import of;
- the consumer is a file in another language and the wire is `++>`: its own source writes its
  imports, so a wire into it declares one, `-->`;
- the consumer is a Jac module and the wire is `-->`: a Jac module writes no import of a project
  module, so a wire into it is the import, `++>`;
- the wire lands in a function or method (`util ++> main.setup { now }`) that the module does not
  declare;
- the wire is for a target (`win ++> host.windows { wide }`) and the module has no file for it:
  no `host.windows.jac`, or, for the targets a plain `host.jac` serves, none left for it to serve.

**Fix:** name each consuming module once per wire, and name one that exists. See
[archwire](../../apps/archwire.md).

## E1143

```text
a wire cannot connect '{module}' to itself
```

A wire in `archwire.jac` has the same module as provider and consumer, as `util ++> util { later }`.
`{module}` is that module. A module already sees its own names.

**Fix:** delete the wire.

## E1144

```text
the import of '{module}' is written in '{consumer}', which takes its imports of the modules under its archwire.jac from wires: {fix}
```

A module under an `archwire.jac` writes an `import` of another module under the same file. There,
imports between the project's own modules are stated as wires and never written in the modules.
That holds for a JavaScript or TypeScript file of the project imported by its path
(`import from "./kit/loud.js" { shout }`): the file is the module `kit.loud`, and a wire brings it.
`{module}` is the module imported, `{consumer}` the module that wrote the import, and `{fix}` is the
exact change to make, such as:

```text
add `util ++> main { now }` to the `graph import` block and delete this import
```

In a target's variant file (`host.windows.jac`) the wire it gives is for the targets that file
serves, as `util ++> host.windows { now }`
([wires for one target](../../language/modules-wiring.md#wires-for-one-target)).

It arises in a project with an `archwire.jac` when, say, `main.jac` holds
`import from util { now }`. Imports of the standard library and of installed packages are written
in the module as usual.

**Fix:** do what `{fix}` says: add the wire it gives to `archwire.jac` and delete the import, or
only delete the import when a wire already brings the name in. See
[archwire](../../apps/archwire.md).

## E1145

```text
module '{module}' has no '{name}'
```

A name is imported from a module, or read through one as `m.name`, and the module has nothing of
that name. `{module}` is the module as the program imports it and `{name}` the name asked for. In a
JS space the same code is reported for a name an npm package does not export, and for one that
jac's own modules there (`@jac/runtime`, `@jac/mobui`) do not: `@jac/runtime` has the names its
space's `ui` plugin gives it, so `Link` is a name of it under React and not under Solid.

```jac
# expect: E1145
import from math { cube_root }

with entry {
    print(cube_root(8.0));
}
```

**Fix:** use a name the module declares. A name that Python's module of the same name has, and the
native one leaves out on purpose, is reported as [E5142](e51.md) with what to write instead. See
[Modules](../../language/modules.md).

Where a native standard-library module is partial and lacks the name (`difflib.unified_diff`),
import CPython's module of the same name explicitly, and call the name on it:
`pydiff = importlib.import_module("difflib");`, then `pydiff.unified_diff(old, new)`. Its results
are Python values; see [Modules that are CPython's](../../library/stdlib.md#modules-that-are-cpythons)
(`jac docs stdlib`).

## E1146

```text
'{name}' is wired into '{consumer}', which never uses it
```

A wire in `archwire.jac` brings a name into a module that never reads it. `{name}` is the name and
`{consumer}` the module. Every name a wire binds must be used where it lands: in code, in a type
annotation, in one of the module's `impl` files, or listed in the module's `__all__`. It arises
from a wire such as `util ++> main { now, later }` when `main` uses only `now`.

**Fix:** remove the name from the wire (`util ++> main { now }`), or use it.

## E1147

```text
'{name}' is declared into '{consumer}' by the '-->' wire at archwire.jac line {line}, but no file of the module writes that import
```

A `-->` wire in `archwire.jac` declares an import that its consumer writes itself, and no file of
the consumer writes it. `{name}` is the name (or module) declared, `{consumer}` the module, and
`{line}` the line of the wire. A `++>` wire is the import; a `-->` wire declares one that the
consumer's own source holds, which is what a file in another language needs: `words --> helper
{ loud }` says that `helper.py` holds `from words import loud`, and it is reported here when
`helper.py` does not. The other direction, an import the source writes and no wire declares, is
[E1575](e15-2.md#e1575).

**Fix:** remove the wire or the name, or write the import in the file. `jac fmt --fix
archwire.jac` removes every such wire and name. See [archwire](../../apps/archwire.md).
